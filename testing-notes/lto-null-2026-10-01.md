# Link-time optimisation: do the plugins make the same audio without it? — 2026-10-01

**Yes, on the input and settings tested, on Windows and on macOS.** The local
half was run on AURORA; the rest by CI. Nothing was listened to, on any
machine: this note says two builds agree sample for sample, and nothing about
how either sounds.

## Why the question came up

The Windows CI job spent 36 to 55 minutes in its Build step even with most
compiles served from the compiler cache. The suspect was link-time
optimisation on the plugin targets: twelve products, VST3 and Standalone each,
and every one of those links regenerates the plugin's own code where no cache
can help. Turning it off for everyday builds and keeping it for release tags
is only safe if a `main` build and a tag build of one commit make the same
audio, because the builds people listen to and test come from `main`.

## What link-time optimisation reaches

Only the plugin targets' own files: the wrapper, the product sources and JUCE.
Read from the generated projects on AURORA (`BMO_LTO=ON`): the plugin targets
carry whole-program optimisation; the module DSP libraries (`bmo_eq_dsp`,
`bmo_reverb_dsp`), `BmoAssets` and the tools do not. The modules' DSP is
compiled the same way in both kinds of build.

## The tool

`tools/fingerprint` (`audio_fingerprint`), added with this change. It loads
each built VST3 as a host does, runs seven seconds of fixed audio through it
and prints a hash of the output per render and one for the whole run. See its
README for what a line means.

- **Input:** an impulse, noise at three levels 12 dB apart, low, mid and high
  tones, a tone with hiss over it, two seconds of silence. Left and right
  differ. Built from integer state and exact float steps, no maths library.
- **Per product:** 48 kHz in 512-sample blocks and 44.1 kHz in 100-sample
  blocks; parameters at their defaults and at three fixed pseudo-random
  positions.
- **The rack:** empty, and with two chains that between them hold all ten
  modules, at defaults and at one random position each.
- **98 renders in all**, each made twice in fresh instances. A render that
  does not repeat is reported and fails the run. None did, anywhere.

## Result

One commit, `9a45d83`, built both ways on each platform.

| where | link-time optimisation | fingerprint | run |
|---|---|---|---|
| Windows, CI | off | `4f571ded8ebf5fdf` | pull-request run 36928297509 |
| Windows, CI | on | `4f571ded8ebf5fdf` | hand-started run 36928301821 |
| macOS (arm64), CI | off | `883cd3418b7f6893` | pull-request run 36928297509 |
| macOS (arm64), CI | on | `883cd3418b7f6893` | hand-started run 36928301821 |
| Windows, AURORA | off | `4f571ded8ebf5fdf` | local Release build |
| Windows, AURORA | on | `4f571ded8ebf5fdf` | local Release build |

Within each platform the two files are identical line for line, all 98
renders, apart from the first line that names the setting. The CI Windows file
and AURORA's are identical too. Windows and macOS differ from each other, as
expected: the tool makes no claim across platforms.

On AURORA the comparison was also made on the audio itself: every render
written out as raw floats outside the repository, 98 files per build, and all
98 pairs byte-identical.

**The builds really are different.** On AURORA the link-time-optimised VST3s
are about 19 % smaller (BMO Opto 6,193,664 bytes against 7,641,088) and the
build log shows twelve code-generation passes at link time against none. In CI
the macOS package is 67 MB with it and 123 MB without; the Windows package is
50 MB either way.

**The tool can see a difference.** Its `diff` mode, given two renders of BMO
Opto at different settings, reports 519,501 of 672,000 samples differing.

## What it cost and what it saves

Build step, the same commit at the same 90.6 % compiler-cache hit rate, CI:

| | with | without |
|---|---|---|
| Windows | 53.4 min | 22.3 min |
| macOS | 19.8 min (89.8 % hits) | 5.4 min (91.6 % hits) |

With a warm cache and no link-time optimisation, an earlier run of the
experiment took 14.4 minutes on Windows and 1.5 on macOS. The fingerprint step
itself takes about a minute per platform.

## What was not done

- **Nothing was heard.** Identical samples on this input is the whole claim.
- **Not every setting.** Four parameter states per product and two rack
  chains. A difference that needs some other setting to appear would not show.
- **No host tempo** is supplied, so nothing tempo-driven is exercised. No
  module on `main` uses the tempo yet; when one does, the tool wants a
  playhead.
- **Intel macOS and the universal build** were not built. Tags build
  universal; these runs were arm64.
- **AU and Standalone** are not loaded. They are the same plugin code behind a
  different wrapper, which is reasoning, not a measurement.
- **Not run on ICE QUEEN.**
- **A release build's time is unknown.** A link-time-optimised run now starts
  with the plugin targets' files cold, and that has not been timed. The job's
  limit for such a run is set wide, at 150 minutes, until a tag has been built.

## How to repeat it

For any commit: let the pull-request or `main` run finish, start the workflow
by hand on the same commit with **lto** ticked, and compare the two runs'
`BMO-<platform>-fingerprint` artifacts. The last line of each should match.
