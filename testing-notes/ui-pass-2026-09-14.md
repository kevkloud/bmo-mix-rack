## 2. The renderer, which was the first real blocker

`docs/ui-workflow-brief.md` §1 proposed a `BMO_UI_ONLY` target because the
machine had no C++ toolchain and every look cost a CI build. **That premise is
stale and the target is not worth building.** Timed here:

| edit | rebuild `snapshot` |
|---|---|
| a tool's own `main.cpp` | 5 s |
| a panel `.cpp` | 4 s |
| a module's `Module.cpp` (an accent) | ~5 s |
| `core/ui/Tokens.h` — worst case | 30 s |

A UI-only target would save at most ~25 s off the worst case for a whole new
build target and a stub-context harness. **Do not build it.**

Setting the worktree up needed two things the handoff does not mention:
`git submodule update --init` (JUCE does not populate into a new worktree) and
a copy of `.bmo-fontdir`.

### What was added instead

- **`Inspect gaps`** (`tools/inspect`, commit `5c7e570`) — runs of bare plate
  down a panel. Exists because `ui_layout_tests --dump` **cannot** answer "is
  this panel too airy": the dump prints control *boxes*, which are nearly
  contiguous, while the ink inside them is not. Read from the dump, Util has
  no empty band worth the name; rendered, its worst is 46 px against EQ's 21.
  The checklist had named the 1 px gap as a result.

- **`theme=<file.json>` on `snapshot`** (`d1e2fd7`) — renders a candidate
  palette without writing the machine-wide `Themes/Default.json`, which every
  open plugin polls at 1 Hz. Read before `appearance=` whatever order they are
  given in, because `appearance` loads the theme. A missing file is fatal.
  **Colour exploration is now zero-rebuild**: six candidate panels in 8.5 s.

- **`utilGain` joined `kEntries`** — it was the only real token missing;
  everything else absent from that list is a derivation.

### The render bug worth remembering

**`snapshot opto` was not reproducible.** Ten renders at a fixed `signal=-18`
gave *three* distinct images. `DynamicsMeter::timerCallback` integrates per
tick at 30 Hz, and the settle loop slept 8 × 40 ms — and `Thread::sleep` is a
floor, not a period, so a scheduler overrun fired an extra tick and the needle
landed 2% further along.

Only Opto showed it: a bar meter quantises to a pixel and swallows 2%, a
needle's angle is continuous and anti-aliased. **The fault was suite-wide and
one panel made it visible.**

It mattered because `inspect hash` is how this project settles whether a
refactor moved anything, and that test was unsound for the one panel with a
needle *in both directions* — a false difference on a pure refactor, and a real
regression dismissible as known flakiness.

Fixed in `7ae1b51` by settling to convergence rather than to looks-settled: 24
ticks leaves 0.72²⁴ = 2.4e-4, so a 25th cannot change a pixel. 8/8 identical
after. Unmetered renders were always deterministic and stay on the short loop.

## 3. Decisions taken, with the numbers they were taken on

### BMO Util — VOLUME takes the utility azure `#4fb8e8` (`aff0282`)

The placeholder `#9c71c3` was hue **271.5°** against Dimension's **271.6°** —
the same hue, so VOLUME read as a Dimension control in a rack. Three candidates
were rendered panel and rack, both appearances:

| | hue | dark plate | pale plate |
|---|---|---|---|
| Util green `#7fc98a` | 128.9 | 6.84 | 1.72 |
| **utility azure `#4fb8e8`** | **198.8** | **6.02** | **1.95** |
| gold `#e8c95a` | 46.9 | 8.33 | 1.41 |

Green cleared the rack and, *rendered*, took VOLUME to the same green as PAN
and WIDTH — the panel went monochrome and the headline knob stopped being the
headline. **No ratio could show that.** Gold read best in the rack and was
recommended; Frosty did not take it, because it puts a section legend at 1.41:1
on the pale plate, below the 1.72–2.00 band the raw-legend rule already spends.

Consequence accepted knowingly: in a rack Util's VOLUME now reads as a trim
knob, since the Saturator's INPUT/OUTPUT are the same azure.

### LTV Comp — the collaboration line (`c273f57`, `a749881`, `d2b8e60`)

Frosty: the vocal compressor is a collaboration, should not read as a BMO
product, and **more collaboration plugins are planned**. So this is a line, not
a one-off.

`ui::Line` owns **surfaces, not ink** — plate, plateEdge, well, knob caps, and
the marque. Not text, accents or meter colours. That boundary is the legibility
rule made structural: a line moves the ground, and every ink still answers to a
known set of grounds. A line owns no layout either.

**A theme beats a line** (`ui::themeSets`, new — `tokens()` returns a colour
and never its provenance). A theme is a statement about the whole window.

| | light | dark |
|---|---|---|
| plate | silver `#c8c8c8` | graphite `#3a3a3e` |
| plateEdge | `#bdbdbd` | `#434347` |
| well | `#b0b0b0` | `#27272b` |
| knob cap | graphite `#3a3a3e` | near-black `#141414` |

Things that were found by rendering and would not have been found otherwise:

- **A plate alone is a trap.** The suite's `well` is `#d6d6d6`, so a silver
  plate at `#d5d5d5` is **1.01:1** against it and every meter trough vanishes —
  the wells stopped appearing in a histogram of the row at all. Hence a ground
  is a *set*. LTV's pair is 1.26:1 / 8.8 L\*, the suite's own relationship one
  step darker.
- **Silver in both appearances fails on a number.** Dark-appearance ink
  `#e6e6ea` on silver is **1.34:1**. It is not a ground change but a request to
  pin the *appearance*, which would make light/dark do nothing on an LTV panel.
  Graphite gives that ink **9.10:1**.
- **The dark plate is the light knob cap** — the same `#3a3a3e`. That is what
  stops the line needing a fifth colour.
- **The pointer follows the cap, not the appearance.** `pointer` is near-black
  in the dark set because a dark cap is normally the accent at full strength; a
  fixed black cap would swallow it. Derived via `onAccentOf` it is white on
  both caps, 11.3:1 and 18.4:1. `Tokens.h` already said this should be so in
  principle.
- Near-black on graphite is 1.63:1 / 18.2 L\*, affordable **only** because
  graphite sits above the suite's dark plate, from which pure black is 1.29:1.

`panelTokensFor` walks up to the panel rather than being plumbed through every
constructor. A rack is why it cannot be a global "current line": JUCE paints
children outside the parent's `paint()`, and a rack holds panels of different
lines side by side.

Latent fault fixed on the way: **`accentInk` derived against the global plate**,
so a legend on an LTV panel would be stepped for `#efefef` and printed on
silver. Nothing visible moved — Vcomp has no labelled rules — but the next LTV
product would have hit it.

### The identity

    name          BMO Vcomp  ->  LTV Comp
    module id     vcomp      ->  ltvcomp
    plugin code   Bvcp       ->  Ltvc
    bundle id     com.lt3audio.bmovcomp -> com.lt3audio.ltvcomp
    presets       .bmovcomp  ->  .ltvcomp, reading .bmovcomp

**LTV codes are two characters for the collaborator and two for the product.**
Frosty's scheme. The capital is required, not style: JUCE's CMake API says
`PLUGIN_CODE` "must contain exactly one upper-case letter" for AU.

**No BMO product is affected**, and that is now written in
`products/AGENTS.md` rather than left to inference. A full Release build still
produces all eight BMO bundles under their original names.

## The three faults worth remembering

- **`snapshot`'s Opto render was not reproducible** -- ten renders, three
  images. `Thread::sleep` is a floor, not a period, so a scheduler overrun fired
  an extra ballistics tick. It made `inspect hash` unsound for the one panel
  with a needle. Fixed by settling to convergence (`7ae1b51`).
- **The panel was silently squashing its own controls.** LOW and HIGH were
  40 px against a trim knob's 78, and `ui_layout_tests` passed --
  `Rectangle::removeFromTop` *clamps*, so a layout that no longer fits does not
  overflow, it shrinks. `checkTrimKnobHeights` is the assertion for it and has
  been seen to fail on the fault.
- **BMO Opto's needle-through-the-zero repeated**, exactly. The gate rested at
  -60, hard left, on top of the printed `60`. Fixed the way Opto's was: put the
  figures where the handle cannot reach, then make the handle unable to reach.
